## Timeline

In September 2025, security researchers identified Shai-Hulud—a self-replicating npm worm that backdoored hundreds of legitimate packages through compromised maintainer accounts [3]. On November 24, 2025, the community detected Shai-Hulud 2.0 ("The Second Coming"), affecting over 796 unique npm packages with combined weekly downloads exceeding 20 million and creating approximately 27,000 malicious GitHub repositories within hours of detection [3][4]. By December 9, 2025, Microsoft documented Shai-Hulud 2.0 as one of the most significant cloud-native ecosystem compromises observed recently in their security blog post published that date [1]. In August 2026 (specifically around mid-August), a new variant dubbed ChainDrop infected over 440 packages with more than 2,200 malicious versions published to the NPM registry and approximately 500 million weekly downloads across the ecosystem. Microsoft updated their guidance on May 13, 2026 noting protection coverage for Mini Shai-Hulud activity resurgence through Defender's enhanced detection capabilities against this renewed campaign variant [4].

## How it spreads

Shai-Hulud worms infect by compromising maintainer accounts from widely used projects (including Zapier, PostHog, and Postman) and injecting malicious code into legitimate package dependencies. The malware adds a preinstall script hook that executes automatically during npm installation before tests or security checks can detect the compromise [3]. This execution phase dramatically widens attack impact because it completely eliminates need for human interaction—guaranteeing execution on virtually every build server processing infected packages and effectively bypasses static scanning tools inspecting code at later build stages where traditional vulnerability assessment might catch malicious content. Attackers harvest credentials from local filesystems, cloud environments (AWS, Google Cloud Platform, Azure), Kubernetes configurations, HashiCorp Vault secrets [7][8]. The malware uses stolen identities to authenticate back into npm registries with compromised publishing tokens, then enumerates available packages under that identity scope before downloading their tarballs. Attackers insert the same malicious loader code (setup_bun.js or setup.mjs files), add preinstall hooks again, increment patch versions artificially so changes appear legitimate in semantic versioning terms [7][8]. This self-replication chain continues without requiring connection back to attacker command-and-control servers—the worm reads its own malicious content from newly published packages and propagates it further through any downstream projects installing those poisoned versions. Shai-Hulud 2.0 introduced a dead man's switch mechanism designed specifically to delete user data if containment is detected, escalating this campaign beyond simple credential theft into denial-of-service attacks that can cripple entire enterprise CI/CD pipelines [4][5]. The campaign exfiltrates stolen credentials and secrets primarily through public GitHub repositories with descriptions such as "Sha1-Hulud: The Second Coming" or later variants using "Shai-Hulud: Here We Go Again," enabling further lateral movement across cloud workloads once attackers have initial foothold via any single compromised package [3][7].

## Remediation steps

Organizations should use private registry proxies combined with Software Composition Analysis (SCA) tools to filter and monitor third-party packages before installation, preventing malicious code from reaching production environments where it could execute during build processes or deployment pipelines. Clear all local package caches completely then reinstall clean versions using strict lockfile enforcement—prefer npm ci over standard npm install—to ensure only exact dependency specifications specified in your project's manifest files execute without running untrusted preinstall scripts that might contain worm propagation code from compromised upstream packages [3][5]. Apply least privilege principles immediately by rotating any potentially exposed credentials: revoke all npm authentication tokens, GitHub personal access tokens (PATs), cloud provider keys and secrets stored as environment variables or configuration files in CI/CD pipelines like GitHub Actions workflows. Enable phishing-resistant multifactor authentication on your accounts across npm registry platform itself plus GitHub platforms where you maintain repositories that could be infection vectors [4][5]. Hunt for Indicators of Compromise including suspicious bundling entries appearing unexpectedly inside package.json files, unexpected additions to existing or new GitHub Actions workflow configurations by unknown users or compromised repository maintainer identities. Monitor abnormal publish patterns from legitimate packages—sudden version bumps with no corresponding code changes in git history that would normally accompany semantic versioning increments [5]. Deploy secret scanning tools within CI/CD pipelines themselves so they detect credential exfiltration attempts as they happen during build execution rather than discovering breaches only after damage has already occurred.
